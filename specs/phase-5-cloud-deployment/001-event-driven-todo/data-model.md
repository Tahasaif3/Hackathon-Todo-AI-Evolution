# Data Model: Event-Driven Todo System

## Core Entities

### Task Event
Represents a state change operation on a task
- **event_id**: UUID (unique identifier for deduplication)
- **event_type**: String (created|updated|completed|deleted)
- **timestamp**: ISO 8601 string (UTC timezone)
- **user_id**: String (authenticated user identifier)
- **task_id**: Integer (reference to the affected task)
- **task_data**: Object (contains title, description, completed status)

### Audit Log
Persistent record of all task events for a user
- **id**: Integer (primary key, auto-increment)
- **event_id**: UUID (foreign key to event, unique constraint)
- **event_type**: String (type of event)
- **user_id**: String (authenticated user identifier)
- **task_id**: Integer (reference to the task)
- **event_data**: JSONB (full event payload)
- **timestamp**: Timestamp with timezone (when event was recorded)

### Task
Core todo item with title, description, completion status, and ownership tied to a user
- **id**: Integer (primary key, auto-increment)
- **title**: String (short description)
- **description**: String (detailed text, optional)
- **completed**: Boolean (completion status)
- **user_id**: String (foreign key to users table)
- **created_at**: Timestamp (ISO 8601 format)
- **updated_at**: Timestamp (ISO 8601 format)

### User
Identity associated with task operations and audit trail access, authenticated via JWT tokens
- **id**: String (unique identifier)
- **email**: String (unique, authentication identifier)
- **created_at**: Timestamp (account creation time)
- **updated_at**: Timestamp (last update time)

## Validation Rules

### Task Event Validation
- event_id must be a valid UUID v4
- event_type must be one of: "created", "updated", "completed", "deleted"
- timestamp must be in ISO 8601 format
- user_id must match authenticated user from JWT
- task_id must reference an existing task owned by the user

### Audit Log Validation
- event_id must be unique within the audit_log table
- user_id must match the authenticated user making the request
- event_data must be valid JSON
- timestamp is auto-generated by the database

### Task Validation
- title must not be empty
- user_id must match authenticated user from JWT
- completed must be a boolean value
- user_id is immutable after creation

## State Transitions

### Task States
- **Created**: New task with completed=false
- **Updated**: Task details modified (title, description)
- **Completed**: Task marked as completed (completed=true)
- **Deleted**: Task removed from user's list

### Event Flow
1. User performs action on task → Backend creates task event → Publishes to Kafka via Dapr
2. Audit service consumes event → Validates user access → Stores in audit_log table
3. User accesses audit trail → Backend verifies JWT → Returns filtered events for user

## Relationships

- **User → Task**: One-to-many (one user owns many tasks)
- **User → Audit Log**: One-to-many (one user has many audit events)
- **Task → Audit Log**: One-to-many (one task may have many audit events)
- **Task Event → Audit Log**: One-to-one (each event creates one audit log entry)
